Item 10 — O contrato de equals()

Sobrescrever equals é assinar um contrato com todo código que já confia em Object — HashMap, HashSet, List. Quebrar uma cláusula não gera erro de compilação: gera bugs silenciosos em produção.

Book Club de Effective Java · item10
“

A forma mais fácil de se evitar problemas é não sobrescrever o método equals.

Antes de tudo

Quando não sobrescrever equals

  1. Cada instância da classe é inerentemente exclusiva.ExemploThread representa uma identidade ativa, não uma identidade de valor.
  2. Não há necessidade de a classe estipular um teste de igualdade lógica.Exemplojava.util.regex.Pattern — o autor diz que essa classe poderia ter sobrescrito equals, mas foi desenhada para não fazer; os engenheiros preferiram não fazer.
  3. Uma superclasse já implementou equals e o comportamento é apropriado para essa classe.ExemploSet herda o equals de AbstractSet, e List herda de AbstractList.
  4. A classe é privada ou package-private.Exemploquando você tem absoluta certeza de que equals não vai ser chamado.
Exemplo — item10/MinhaThread.java

Instância inerentemente exclusiva

MinhaThread.javaextends Thread
package dev.matheuscruz.item10;

public class MinhaThread extends Thread {}

Cada Thread representa uma execução real e única do sistema — não existe "igualdade lógica" entre threads. Sobrescrever equals aqui pode apagar essa identidade ativa e quebrar qualquer coleção ou lógica que dependa dela.

Mas…

Mais cedo ou mais tarde, vamos precisar implementá-lo

Na prática, é raro nunca sobrescrever equals. Alguma classe do seu domínio vai exigir igualdade lógica. A pergunta certa não é se — é quando.

Quando implementar

Quando o valor importa mais que a identidade

Em DDD (Domain-Driven Design), um Value Object é definido pelos seus atributos, não por uma identidade própria — dois objetos de valor são iguais quando todos os seus atributos são iguais. Costumam ser imutáveis e substituíveis entre si.

Dinheiro
R$ 10,00 — igual a qualquer outro R$ 10,00
CPF / Email
o valor é a identidade do objeto
Coordenada
Point(x, y) — dois pontos, mesmo valor

É exatamente aqui que equals se torna necessário: comparar por valor, não por referência.

Como implementar corretamente?

equals deve ser…

  1. Reflexivo
  2. Simétrico
  3. Transitivo
  4. Consistente
1 · Reflexividade

x.equals(x) precisa ser true

Sendo x não nulo, x.equals(x) deve retornar true.

2 · Simetria

x.equals(y) precisa concordar com y.equals(x)

Sendo x e y não nulos, x.equals(y) e y.equals(x) devem retornar ambos true.

3 · Transitividade

x=y e y=z devem implicar x=z

Sendo x, y e z não nulos: se x.equals(y) e y.equals(z), então x.equals(z) também deve ser true.

É a cláusula mais complexa de explicar — voltamos nela em detalhe daqui a pouco.

É aqui que ela quebra

A violação da transitividade aparece quando temos herança: uma superclasse já tem equals, e uma subclasse adiciona um componente de valor tentando manter o contrato.

O ponto de partida

Obedece
Point.java
@Override
public boolean equals(Object obj) {
    if (!(obj instanceof Point point)) return false;
    return point.x == this.x && point.y == this.y;
}
item10/transitividade/ColorPoint.java

ColorPoint extends Point — e agora?

ColorPoint adiciona um componente de valor (color) a uma classe que já é instanciável e já tem equals. O arquivo guarda duas tentativas comentadas de resolver isso.

Consequências

Temos diversos problemas

  • Violação da simetria — o resultado muda dependendo de quem compara com quem.
  • Violação da transitividade — dois pares "iguais" não garantem que o terceiro também seja.
  • Violação do Princípio de Substituição de Liskov — o comportamento de equals muda conforme o tipo concreto.
Duas tentativas

E nenhuma resolve os três problemas ao mesmo tempo

Opção A — só compara com ColorPoint

Quebra simetria 
if (!(obj instanceof ColorPoint c))
    return false;
return super.equals(obj)
    && c.color == this.color;

Opção B — ignora a cor ao comparar com Point

Quebra transitividade e Liskov 
if (!(obj instanceof Point p)) return false;
if (!(obj instanceof ColorPoint))
    return obj.equals(this);
return super.equals(obj)
    && ((ColorPoint) obj).color == color;
Princípio de Substituição de Liskov

Em poucas palavras

Se S é subtipo de T, qualquer código escrito para T deve continuar funcionando corretamente ao receber um S no lugar — sem checagens especiais, sem surpresas.

Quando o equals de ColorPoint se comporta de forma diferente dependendo de quem está do outro lado da comparação, código que trata todo Point da mesma forma passa a se comportar de modo inconsistente ao receber um ColorPoint. A substituição deixa de ser segura.

A opção B, posta à prova

O contraexemplo clássico

p1 = new ColorPoint(1, 2, RED)
p2 = new Point(1, 2)
p3 = new ColorPoint(1, 2, BLUE)
p1.equals(p2) → true // p2 não é ColorPoint, cor ignorada
p2.equals(p3) → true // mesma razão
p1.equals(p3) → false // ambos são ColorPoint — cores diferem
Uma terceira tentativa — ColorPoint.java

Opção C — getClass() em vez de instanceof

Quebra Liskov
equalssó compara dentro do mesmo tipo exato
if (obj == null || obj.getClass() != getClass())
    return false;
Point p = (Point) obj;
return p.x == x && p.y == y;
p1 = new ColorPoint(1, 2, RED)
p2 = new Point(1, 2)
p1.equals(p2) → false // getClass() difere
p2.equals(p1) → false // simétrico, ao menos

Simetria e transitividade voltam a valer — mas ao custo de ColorPoint nunca poder ser igual a um Point, mesmo quando isso seria o comportamento esperado. O próprio comentário do código já entrega o veredito.

Como resolver?

Não existe forma satisfatória — mas há uma alternativa

Composição em vez de herança: ColorPoint não é um Point — ele tem um Point.

Obedece
composição, não herança
public class ColorPoint {
    private final Point point;
    private final Color color;

    public ColorPoint(int x, int y, Color color) {
        this.point = new Point(x, y);
        this.color = Objects.requireNonNull(color);
    }

    public Point asPoint() { return point; }

    @Override
    public boolean equals(Object o) {
        if (!(o instanceof ColorPoint cp)) return false;
        return cp.point.equals(point) && cp.color.equals(color);
    }
}
